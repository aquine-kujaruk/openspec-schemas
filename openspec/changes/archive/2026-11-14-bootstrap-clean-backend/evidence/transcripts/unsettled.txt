# app-domain

**Owns:** `test/acceptance/<module>/` (one step adapter per use case, next to the test generated from its product spec), `src/<module>/application/` (use cases and repository interfaces) and `src/<module>/domain/` (entities, aggregates, value objects, schemas, exceptions, services).

**Receives:** the product specs, one per use case under the configured product specs root (`openspec/specs/<module>/<use-case>/spec.md` by default), and nothing from other workstreams. The repository interfaces it declares are seams that `infrastructure` implements. The change's design defines them (which methods, which props and exceptions), and the implementer fixes them before this workstream starts.

**Fakes:** repositories, and only them. Acceptance is a black box against the use case. Each repository the use cases need has an in-memory twin in `test/acceptance/<module>/repositories/in-memory-<name>.repository.ts`: `class InMemory<Name>Repository implements <Name>RepositoryInterface`, with no constructor parameter and a `seed(...)` method the Given steps call. It behaves like the one infrastructure will build: same contract, same exceptions of the module family. It never imports from `infrastructure`.

## How

1. Read the `## reference` sections of `acceptance.examples.md`, `application.examples.md` and `domain.examples.md`: they are the shape of correct code. The other sections show each way of breaking a rule.
2. `pnpm exec factory generate`: each product spec becomes `test/acceptance/<module>/<use-case>.feature.test.ts` and a step adapter `<use-case>.feature.steps.ts` with a pending method per step. Never write or edit a test file; a behavior the spec lacks goes back as feedback on the change.
3. Write the in-memory repositories, fill the step adapter of each use case, then write the use case and the domain it needs, until `pnpm exec factory test acceptance` is green. A step method keeps its parameter names equal to the spec's placeholders, or the next generation scaffolds it again. Steps check their data with assertions (`expect`), never `throw new Error(`; the `PENDING` bodies feat2test scaffolds break that rule, so the pipeline is red until every step is written.
4. The module's exceptions are the family the design declares: one base extending `DomainException`, one subclass per business failure.
5. Follow the core-wide rules even though `clean-architecture` checks them: no `any` in the core, only domain exceptions (the provider error in `cause`), the schema package only in `domain/schemas`.

**Check:** `pnpm exec factory check --workstream app-domain [--module <module>]`, plus `pnpm exec factory test acceptance`.

import type { InvoiceRepositoryInterface } from "../../../../src/module/application/repository-interfaces/invoice.repository-interface";
import type { InvoiceProps } from "../../../../src/module/domain/schemas/invoice.schema";
export class InMemoryInvoiceRepository implements InvoiceRepositoryInterface {
  private invoices: InvoiceProps[] = [];
  seed(invoices: InvoiceProps[]) {
    this.invoices = invoices;
  }
  async listInvoices() {
    return this.invoices;
  }

    return this.invoices.find((invoice) => invoice.id === invoiceId) ?? null;

import { expect } from "vitest";
import { ListInvoicesUseCase } from "../../../src/module/application/use-cases/list-invoices.use-case";
import { InvoiceStatus } from "../../../src/module/domain/schemas/invoice.schema";
import { InMemoryInvoiceRepository } from "./repositories/in-memory-invoice.repository";
export function createSteps() {
  const invoices = new InMemoryInvoiceRepository();
  let listed = 0;
  return {
    async invoicesStored(count: string) {
      invoices.seed(
        Array.from({ length: Number(count) }, (_, i) => ({
          id: `i${i}`,
          total: 100,
          status: InvoiceStatus.PAID,
        })),
      );
    },
    async invoicesListed() {
      listed = (await new ListInvoicesUseCase(invoices).execute()).length;
    },
    async invoicesReturned(count: string) {
      expect(listed).toBe(Number(count));
    },
  };
}

export const validateSchema = <S extends z.ZodType>(
  target: object,
  schema: S,
  props: unknown,
): z.output<S> => {
  const result = schema.safeParse(props);
  if (!result.success) throw new ValidationException(target.constructor.name, result.error);
  Object.assign(target, result.data);
  return result.data;
};

# feedback

Feedback goes back into the change it is about, whoever raised it: `the person`, `the completion gate`, `the verify phase`, `the archive` or `the implement phase`.

1. `pnpm exec factory doctor`. When it prints anything as `missing` or `drift`, follow the `setup` skill first. A `note` is for the person: relay it once and go on.
2. `pnpm exec factory feedback <change>` lists what was raised and is waiting. What the person just said is feedback from `the person`.
3. For each piece of feedback, settle two things:
   - the earliest phase whose work it undoes, or none when it only adds to what is left;
   - the decisions it needs that only the person can take, by the question policy in the plan's instruction (`pnpm exec factory openspec instructions plan --change <change> --json`). Something neither the plan nor you can settle, such as a defect of the harness or an access you lack, is a question for the person too.
4. Take it in:

   ```bash
   pnpm exec factory feedback <change> take --from "<source>" --says "<what it said and what changes>" --phase <n> --ask "<question>"
   ```

   Leave `--phase` out when no phase is undone, and give one `--ask` per question. The command adds the entry under Feedback, unchecks the tasks of phase `<n>` and of every phase after it, and lists each question under Open questions.
5. Update what the feedback changes: the plan's decisions, seams and tasks, and the delta specs when behaviour is affected. Everything goes into this change.
6. `pnpm exec factory validate <change>`. With open questions the change waits for the person: show them and stop. Once it prints `ready`, the `implement` skill goes on from the first phase with unchecked tasks.

# Gherkin Craft

Input: requirements for programmed software. Output: Gherkin whose named steps
map to Step Adapter methods and whose examples drive the tests feat2test
generates. Read [the generator contract](references/generator-contract.md) and
[format and language](references/gherkin-format.md) before writing or
reviewing. Use [the authoring guide](references/authoring-guide.md) for worked
examples when choosing a formulation.

## Every step is named

End every step with one HTML comment naming its Step Adapter method:
`When <quantity> units are added <!-- addUnits -->`. The name is the step's
identity and the words are documentation; feat2test rejects a step without one
(`MISSING_STEP_NAME`) or with a malformed one (`INVALID_STEP_NAME`). Names are
camelCase, English by default, representative and semantically loaded: they
state the action or fact (`<!-- confirmOrder -->`), never a position or filler
(`<!-- step1 -->`, `<!-- doIt -->`). Give one fact one name across the Feature,
even where its wording differs, and keep each name to one keyword role and one
input shape. Markdown preview hides the names; they stay visible in the source
and in `.feature` files, and no other marker syntax replaces them.

Put every value that varies between examples in a placeholder, never in the
words. Bind every placeholder in every row, including those in titles and
DataTables, which the generator does not catch. The generated test only calls
steps, so each Then step carries the value it checks
(`the order total is <total> <!-- orderTotal -->`), not a verdict
(`the total is correct <!-- totalIsCorrect -->`).

## One Feature per use case

Each Feature is one complete use case at the software's boundary: relevant prior
facts, one whole action or query, and the observable answer or changed or
preserved state. Rules and outcome variants of that use case, acceptance and
rejection included, stay together in distinct scenarios. Distinct purposes get
separate Features even when they share data; shared quantities keep one meaning.
No human actor is required when the domain has none.

Specify what the software answers, changes or preserves, not how. Replace a step
that describes implementation
(`the repository save method is called <!-- repositorySaveCalled -->`) with its
observable result. Internal call order, algorithms, runners, languages and
output layout are not acceptance criteria and never become steps or Examples
columns.

## Meaningful arguments

- Expose identities, quantities, units, categories, relative positions,
  negative facts and expected results as named arguments in a
  `Scenario Outline`, even with one justified row.
- Keep independently variable roles apart even when their values coincide: a
  horizon, a reporting interval and a recurrence interval of seven days are
  three arguments with explicit units, not one `days`.
- Keep a cohesive record or collection as one DataTable, not many scalar
  columns. To vary whole records, give each an identity in the table and select
  it from Examples.
- Keep fixed rule criteria fixed. A diagnostic may bind the fixed value without
  making the criterion configurable. Never replace actions, conditions or
  diagnostics with prose-valued arguments such as `<reason>`.
- Preserve subjects, negation, quantifiers, units, timing, relative selectors
  and causes. Use explicit absence, not blank cells or `null`. Supply raw input
  when its derivation is what the use case examines.

## Discriminating examples

Ask whether each example would still pass if a factor or rule were ignored; a
factor of one hides a missing multiplication. Cover meaningful partitions,
boundaries and failures, and keep unknown, absent, zero and invalid distinct.
Recognize coverage already present and keep it on revision.

A boundary belongs here when the domain expert would recognize it as their rule:
a zero price, a repeated item, an amount shown with two decimals. A value that
matters only because of machine representation (binary floating point, time
zones, text normalization, overflow) is left out and named as a candidate for
downstream programmatic tests, which are not written in Gherkin.

Inspect relevant state/event pairs, repeated requests, missing information and
mixed independent dimensions. A rejection states what was preserved; a query
checks its answer without inventing a mutation. Each scenario supplies its own
context and never depends on another having run. Parsing or a small
cross-product does not prove exhaustive coverage.

## Unresolved rules stay out of tables

Separate what the requirements assert, what is justifiably inferred and what is
undecided. When a row's expected outcome depends on an undecided rule, such as a
rounding or validity policy, omit that row, state the open decision and deliver
the supported rows. One supplied instance exposes a relationship's arguments; it
does not establish behavior for members the source does not support.

## Tags

Tags are metadata the generator does not interpret. None is required, including
`@code`; they only serve the project's own runner filters or conventions.
Preserve tags already present when revising.

## Validate with the generator

When feat2test is installed, run `feat2test validate` on the delivered Feature
through its file, `--text` or `--stdin`, with the project's runner and `--json`.
Report the example count and diagnostics; it writes nothing. When it is not
installed, check the format reference and say generator validation was not run.
Validation proves generability, not semantic review.

Write specifications in English unless the user or the project's `CLAUDE.md` or
`AGENTS.md` explicitly asks for another language for them. Method names stay
English unless the user explicitly asks for another language for the methods

# Generator step contract

Read before writing or reviewing any step. feat2test turns each Feature into a
Feature Test that only calls steps, and a Step Adapter with one method per
distinct step name. These rules are mechanical; breaking them either fails
generation or silently produces the wrong methods.

## A step's name is its method

Every step ends with one HTML comment holding its adapter method name:

```gherkin
Feature: Add units
  Scenario Outline: Add <quantity> units
    Given an empty cart <!-- emptyCart -->
    When <quantity> units are added <!-- addUnits -->
    Then the cart contains <quantity> units <!-- cartContains -->

    Examples:
      | quantity |
      | 2        |
```

The name is the step's identity; the words before it are documentation. The
comment closes the step line, after any placeholder; a DataTable or DocString
follows on the next lines. Markdown preview hides it, while the `.feature.md`
source and native `.feature` files show it.

| Step text | Method |
| --- | --- |
| `the cart holds <quantity> items <!-- cartHolds -->` | `cartHolds(quantity: string)` |
| `the cart contains <quantity> items <!-- cartHolds -->` | `cartHolds(quantity: string)` |
| `el carrito contiene <quantity> artículos <!-- cartHolds -->` | `cartHolds(quantity: string)` |
| `the cart holds <quantity> items <!-- cartStillHolds -->` | `cartStillHolds(quantity: string)` |
| `the cart holds 2 items <!-- cartHoldsTwoItems -->` | `cartHoldsTwoItems()` |

So:

- Steps with one name call one method, whatever their words or language.
  Steps with different names are different methods, even with identical words.
  Give one fact one name across the Feature.
- Rewording a step keeps its method and implementation. Renaming it creates a
  new pending method and drops the old one once no step uses it. Changing only
  Examples values keeps the method and its implementation.
- A value that varies between examples is a placeholder, not a word. A literal
  `2 items` is part of the documentation, never a parameter.
- Names are English unless the user explicitly asks otherwise, and
  representative: they state the action or fact (`confirmOrder`,
  `orderTotal`), never a position or filler (`step1`, `doIt`).

## Names the generator accepts

The generator checks only the identifier format: `^[a-z][A-Za-z0-9]*$`, and
not a JavaScript reserved word. It cannot tell whether a name is English or
representative; that judgment is the author's.

- A step without a trailing name comment fails with `MISSING_STEP_NAME`.
- A name with spaces, hyphens, accents, a leading digit or capital, or a
  reserved word such as `delete`, fails with `INVALID_STEP_NAME`. So does a
  second comment in the same step, or a comment that does not end it.

Both name the source, line and step, and are reported before any file is
written. A trailing HTML comment in a step is always read as its name; put
explanations in a description or a comment line instead.

## Inputs become parameters

- Each distinct `<name>` in the step text becomes a `string` parameter, in
  order of first occurrence. A placeholder repeated in one step is one
  parameter. The parameter name is the placeholder name with its first letter
  lower-cased and any character that cannot appear in an identifier removed.
- A DataTable becomes a final `table: string[][]` parameter: every row,
  including the header, as strings.
- A DocString becomes a final `text: string` parameter.
- Every value arrives as a string. Numbers, money and dates are parsed by the
  adapter, never by the generator.

The parameter list is part of the signature. The same name used with a
different placeholder name, or once with a DataTable and once without, fails
with `CONFLICTING_STEP_INPUTS`.

## Keywords set the role

`Given` is Context, `When` is Action and `Then` is Outcome. `And`, `But` and
`*` inherit the role of the previous step; a scenario that starts with `*`
starts in Context. Background steps run first in every scenario. The same
name with two roles, for example `<!-- orderConfirmed -->` on a Given and on a
Then, fails with `CONFLICTING_STEP_ROLE`. Rename one of them.

## Examples bind placeholders

Each Examples row becomes one test and supplies the values for every
placeholder in that expansion. Repeated titles are numbered (`#2`, `#3`). The
name comment is never a placeholder.

- A placeholder in the step text with no Examples column, or in a plain
  `Scenario`, fails with `UNKNOWN_PLACEHOLDER`.
- A placeholder in a scenario title or a DataTable cell with no column does
  **not** fail: it stays as the literal text `<name>` in the test name or the
  table value. Check those bindings by hand.

## Generated tests only call steps

The Feature Test is rewritten on every generation and contains no
assertions. Each step becomes one call, in order, with its values as string
literals, below a comment with its keyword and words but not its name. Every
check lives in the adapter method of a Then step, which receives nothing but
its parameters. A Then step therefore carries the value it checks
(`the order total is <total> <!-- orderTotal -->`), never a judgment the
method cannot compute from its inputs
(`the total is correct <!-- totalIsCorrect -->`).

## Tags are ignored

Feature, Rule and Scenario tags are parsed and discarded. They do not change
the generated test, the adapter or the runner.

## Check with the generator

```bash
npx feat2test validate <feature> --runner vitest --json
npx feat2test validate --text '<feature text>' --format feature --source draft.feature --runner vitest --json
```

Use `--format mdg` for Markdown, or `--stdin` instead of `--text`. Validation
writes nothing. It reports `scenarioCount` (expanded examples), `stepCount`
(distinct methods), warnings for table rows that will not parse as intended
(a separator row in a native file, a Markdown row without two leading spaces),
and the diagnostics above. It proves generability only, not that the
specification is right.
# Format and language

Read for all authoring and review. Preserve the requested representation;
formatting choices must not change the domain claim.

## Language

Specifications are English by default. Write them in another language only when
the user, or the project's agent instructions (`CLAUDE.md`, `AGENTS.md`),
explicitly request it for the specifications, including a request to retain an
existing specification's language. Conversing in another language is not such a
request. Apply the choice to titles, descriptions, sentences, and argument
names. Preserve proper names, identifiers, contractual literal data, and terms
required verbatim. Use established translations consistently; resolve material
ambiguity from context or ask. Teaching examples in this skill remain English.

Step method names are a separate choice and stay English camelCase even in a
specification written in another language: `Dado un carrito vacío <!-- emptyCart -->`.
Use another language for them only when the user explicitly requests it for the
method names too; then write them as camelCase identifiers without accents or
spaces (`<!-- carritoVacio -->`). The generator checks only that identifier
format, not the language.

For non-English output, use native `.feature` unless the user explicitly
requires Markdown. Begin native output with `# language: <code>` using a
supported Gherkin dialect, then use that dialect's keywords throughout. The
directive is literally `language`, not a tag or YAML. English uses `en` and
needs no declaration.

If non-English Markdown is explicitly required, resolve the consumer's external
dialect configuration before claiming valid output. A native per-file language
directive does not configure Cucumber's Markdown dialect. Explain the constraint
and offer native `.feature` when a self-contained declaration is needed; do not
silently switch a requested format or invent a Markdown language attribute.

## Common structure

- A Feature contains one use case; Rule groups one governing rule; Scenario is
  one observable example. When writing files, give each Feature its own file.
- Given supplies prior facts; When names the whole action or query; Then states
  its answer and relevant changed or preserved facts. And/But continue the
  preceding role. But provides contrast, not automatic negation.
- Every step line ends with its method name comment, `<!-- name -->`, in both
  formats; a DataTable or Doc String follows on the next lines.
- Each Examples row is independent. Group rows by intent and kind of outcome;
  acceptance and rejection use different scenarios within the same use case.
  One Outline may carry several titled Examples blocks: the first illustrates
  the rule with a reader-friendly case; later blocks hold the boundaries the
  expert confirmed. The split is presentation only; every row is one scenario.
- A Scenario Outline exposes meaningful scalar arguments even for one row.
  Every placeholder has a concrete Examples binding, including occurrences in
  titles, DataTables, and consequences. Plain Scenarios suit argument-free cases.
- DataTables describe a cohesive record or collection within one example;
  Examples tables describe behavioral variation. Use Doc Strings for coherent
  source text. Do not serialize an aggregate or reproduce a constructor.
- Titles state the outcome and relevant condition, understandable on their own.
  Avoid “happy path” and numbered case labels as their only meaning.
- Background contains only preconditions shared by every example in its scope,
  never varying data, actions, or assertions. Prefer repetition when it avoids
  making the reader search for essential context. Tags are metadata.
- Use concrete values, digits for numerical counts/positions, and explicit
  presence or absence. Do not use blank cells or nullish stand-ins for missing
  facts. Preserve literal source content when it is actually being examined.

## Native `.feature`

Use native keyword structure, indentation for readability, and ordinary bare
Outline placeholders. A DataTable follows its step. Do not add Markdown heading
markers, bullet steps, or Markdown formatting separator rows. In native tables,
those separators become data, including additional Examples cases.

Tags are metadata the generator ignores; in a non-English file they follow the
`# language: <code>` line.

## Markdown `.feature.md`

Use Gherkin headings and bullet steps, for example `# Feature:`, `## Rule:`,
`### Scenario Outline:`, `#### Examples:`, and `* Given ...`. Use native syntax
only in native files; a fenced native document is not Markdown Gherkin structure.
Only recognized headings, steps, tables, and backtick tags have Gherkin meaning;
other prose remains documentation. Markdown preview hides each step's
`<!-- name -->` comment; it remains in the source, where the generator reads it.

Write each tag in its **own** backtick span, for example `` `@billing` `@slow` ``.
A single span containing several tags parses as one compound tag, and native
bare tag syntax in Markdown is ordinary prose.

Use two leading spaces on every table row so Examples and DataTables are
recognized. Insufficient indentation may silently hide a table.

Cucumber's Markdown parser accepts header separators such as `| --- |`,
including left, right, and centered alignment markers. These are formatting:
they do not add Examples cases or DataTable values. Tables without separators
are also supported. Do not report a separator as data corruption solely because
it appears in Markdown; verify the intended rows and values with the consumer.

Backticks around placeholders in headings or sentences protect their Markdown
rendering. Inside Examples cells, DataTable cells, and Doc String contents, use
plain values and bare placeholders. Formatting backticks there become literal
data. Ordinary explanatory Markdown tables outside specifications can use normal
Markdown separators; do not confuse them with Gherkin tables.

## Verify interpretation

Where `feat2test validate` or another parser is available, inspect expanded
example counts, bindings, selected dialect, and resulting step/table values.
Check all intended rows survived and formatting did not become data. Successful
parsing is not a semantic review and does not demonstrate domain execution.
