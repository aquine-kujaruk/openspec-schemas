# feedback

Feedback goes back into the change it is about, whoever raised it: `the person`, `the completion gate`, `the verify phase`, `the archive` or `the implement phase`.

1. `pnpm exec factory doctor`. When it prints anything as `missing` or `drift`, follow the `setup` skill first. A `note` is for the person: relay it once and go on.
2. `pnpm exec factory feedback <change>` lists what was raised and is waiting. What the person just said is feedback from `the person`.
3. For each piece of feedback, settle two things:
   - the earliest phase whose work it undoes, or none when it only adds to what is left;
   - the decisions it needs that only the person can take, by the question policy in the plan's instruction (`pnpm exec factory openspec instructions plan --change <change> --json`).
4. Take it in:

   ```bash
   pnpm exec factory feedback <change> take --from "<source>" --says "<what it said and what changes>" --phase <n> --ask "<question>"
   ```

   Leave `--phase` out when no phase is undone, and give one `--ask` per question. The command adds the entry under Feedback, unchecks the tasks of phase `<n>` and of every phase after it, and lists each question under Open questions.
5. Update what the feedback changes: the plan's decisions, seams and tasks, and the delta specs when behaviour is affected. Everything goes into this change.
6. `pnpm exec factory validate <change>`. With open questions the change waits for the person: show them. Once it prints `ready`, the `implement` skill goes on from the first phase with unchecked tasks.

# app-domain

**Owns:** `test/acceptance/<module>/` (one step adapter per use case, next to the test generated from its product spec), `src/<module>/application/` (use cases and repository interfaces) and `src/<module>/domain/` (entities, aggregates, value objects, schemas, exceptions, services).

**Receives:** the product specs, one per use case under the configured product specs root (`openspec/specs/<module>/<use-case>/spec.md` by default), and nothing from other workstreams. The repository interfaces it declares are seams that `infrastructure` implements. The change's design defines them (which methods, which props and exceptions), and the implementer fixes them before this workstream starts.

**Fakes:** repositories, and only them. Acceptance is a black box against the use case. Each repository the use cases need has an in-memory twin in `test/acceptance/<module>/repositories/in-memory-<name>.repository.ts`: `class InMemory<Name>Repository implements <Name>RepositoryInterface`, with no constructor parameter and a `seed(...)` method the Given steps call. It behaves like the one infrastructure will build: same contract, same exceptions of the module family. It never imports from `infrastructure`.

## How

1. Read the `## reference` sections of `acceptance.examples.md`, `application.examples.md` and `domain.examples.md`: they are the shape of correct code. The other sections show each way of breaking a rule.
2. `pnpm exec factory generate`: each product spec becomes `test/acceptance/<module>/<use-case>.feature.test.ts` and a step adapter `<use-case>.feature.steps.ts` with a pending method per step. Never write or edit a test file; a behavior the spec lacks goes back as feedback on the change.
3. Write the in-memory repositories, fill the step adapter of each use case, then write the use case and the domain it needs, until `pnpm exec factory test acceptance` is green. A step method keeps its parameter names equal to the spec's placeholders, or the next generation scaffolds it again. Steps check their data with assertions (`expect`), never `throw new Error(`; the `PENDING` bodies feat2test scaffolds break that rule, so the pipeline is red until every step is written.
4. The module's exceptions are the family the design declares: one base extending `DomainException`, one subclass per business failure.
5. Follow the core-wide rules even though `clean-architecture` checks them: no `any` in the core, only domain exceptions (the provider error in `cause`), the schema package only in `domain/schemas`.

**Check:** `pnpm exec factory check --workstream app-domain [--module <module>]`, plus `pnpm exec factory test acceptance`.

# List customer orders

## Goal

Provide a query returning a customer's orders with id, customer id, total in cents and placement date, newest first. Deliver the use case and domain with acceptance coverage first; then connect the repository, anti-corruption layer, HTTP and development adapters, and entry.

## Decisions

- Use the `orders` module and `ListCustomerOrdersUseCase.execute(customerId)` returning order props, rather than introducing an inbound web server the request does not require.
- The application sorts by placement instant descending, rather than relying on backend ordering; equal instants have no additional public ordering guarantee.
- Return a complete array without pagination, rather than inventing a paging protocol absent from the service contract.
- Keep placement dates as validated ISO timestamp strings in props and compare their parsed instants, rather than comparing strings or exposing mutable Date objects.
- Map resource records to domain props in the repository; retain snake_case only in the ACL and adapters, rather than letting the service vocabulary enter the use case.
- Use `NODE_ENV=development` for the in-memory backend (empty by default, constructor-seedable); all other environments use HTTP and require `ORDERS_API_URL`, rather than silently falling back to development data.
- Translate invalid records to `ValidationException` and resource/configuration failures to `OrdersUnavailableException` with the original error as cause; reject the query rather than returning partial data or disguising failure as an empty list. No retry policy or public HTTP error status is introduced.
- Use generated acceptance tests with a fake repository in phase 1 and repository integration tests with an ACL-typed in-memory adapter in phase 2, rather than real network calls in local tests.
- The cents architecture decision below is explicitly requested by the user; it is already authorized.

## Open questions

- For a customer with no orders: return an empty list or report an error? Pick an empty list: it preserves the array query contract. The proposed spec and tests below assume this option pending confirmation.

## Architecture decisions

### Decision: money-in-integer-cents · Money amounts use integer cents

@adds @area:product @topic:money @applies:domain,application,infrastructure,adapters @enforced:domain-and-acl-schemas,integration-tests,review

Money amounts SHALL be represented as integers in cents across the product. `OrderProps.totalCents` and service `total_cents` SHALL carry the same cents value without division, rounding or conversion into floating-point major currency units. JavaScript number values SHALL pass safe-integer validation so the representation preserves exact cents.

**Why** The user explicitly requires integer cents; retaining that unit avoids rounding and unit ambiguity at boundaries.

**Alternatives** Decimal major units and floating-point currency values are discarded because they weaken the required representation.

**Consequences** Future money fields must preserve this unit. Values outside the safe-integer range are rejected, not rounded. Currency, sign restrictions and exchange rates are outside this decision.

```ts src/shared/domain/schemas/validation.schema.ts
import type { z } from "zod";
import { ValidationException } from "../exceptions/validation.exceptions";
export const validateSchema = <S extends z.ZodType>(
  target: object,
  schema: S,
  props: unknown,
): z.output<S> => {
  const result = schema.safeParse(props);
  if (!result.success) throw new ValidationException(target.constructor.name, result.error);
  Object.assign(target, result.data);
  return result.data;
};
```

# integrate

**Reduces:** the workstreams the topology lists under it (by default `clean-architecture`).

**Owns:** the checks that only make sense once everything is wired:

- `no-unused-files`: no file of the product is left unused. Everything is reached from the entry or from a test; the HTTP and in-memory adapters are both reachable because `x.adapter.ts` picks one by environment.
- `duplication-below-threshold`: global duplication under 4 %. A block repeated in two modules is a candidate for `shared`. The generated acceptance tests are skipped: they repeat by design.

## How

1. Merge the upstream work; the entry is where the use cases, the repositories and the adapters meet.
2. Run the check. It is the full pipeline: every workstream's rules, these two checks and the freshness of the generated tests. End-to-end tests will live here once `test/e2e` has them.

**Check:** `pnpm exec factory check --workstream integrate`; `pnpm exec factory check` adds the freshness of the generated tests.

description: Run the clean-architecture reduce workstream of the implementer: merge app-domain, infrastructure and adapters, resolve conflicts at their seams and pass the cross-module rules. Read from the implement skill.

# clean-architecture

**Reduces:** the workstreams the topology lists under it (by default `app-domain`, `infrastructure` and `adapters`).

**Owns:** the cross-module rules (`modules.rules.ts`): modules do not import one another, `shared` imports no module, no cycles, every file in a zone, no tests in `src`, no `any` and no raw errors in the core, and no escape from the harness (a lint rule disabled, a type error suppressed or expected, a cast through `unknown`). It also owns the entry (`src/main.ts` by default), the composition root: the only place that builds adapters, repositories and use cases together.

## How

1. Merge the upstream workstreams' work. A conflict can only be at a seam: if both sides changed a repository interface or an ACL, the seam was not fixed first; settle it on what the consumer needs (the use case for a repository interface, the repository implementation for an ACL) and adapt the other side.
2. Run the check. This is where it shows whether each map workstream built what its spec, its skill and its seams asked for. A failure names the workstream: go back to it and fix it there, keeping the seams and the artifacts as they are, then run this check again. A decision the artifacts do not settle and you cannot take goes to the person, as the implement skill says.
3. Fix what crosses modules: move what two modules share into `shared`, break cycles.

**Check:** `pnpm exec factory check --workstream clean-architecture [--module <module>]`, which includes every upstream workstream's check.

# implement

One run builds one phase: the first phase of the plan that has an unchecked task.

1. `pnpm exec factory doctor`. When it prints anything as `missing` or `drift`, follow the `setup` skill first. A `note` is for the person: relay it once and go on.
2. `pnpm exec factory validate <change>`. Build only a change it prints as `ready`; for any other, tell the person what it found and stop.
3. `pnpm exec factory prepare`, then `pnpm exec factory generate`. The acceptance tests of the change's delta specs appear under the acceptance root, each next to its step adapter. A generated test is written only by that command: a behaviour it lacks is feedback on the change.
4. Write every seam the phase declares, signed exactly as the plan signs it, before the first task starts.
5. Take the phase's tasks in order. For each one, read `references/workstreams/<workstream>/SKILL.md` and the example files beside it, do the task inside that workstream's folders, run that workstream's check until it passes, and tick the task in the plan.
6. Keep the entry up to date. The entry (`src/main.ts` unless the project configures another) belongs to `clean-architecture`: it builds each adapter, hands it to its repository implementation, and hands the repositories to the use cases. Create it with the first use case and extend it with every use case, repository and adapter, so that every file of the product is reached from it or from a test.
7. The phase's last task verifies it: run the check of the workstream it names, tick it when it passes, and stop. The next phase is another run.

Decide alone what only the code needs: a private name, a helper, the order of the work. # List customer orders

## Goal

Provide a query returning a customer's orders with id, customer id, total in cents and placement date, newest first. Deliver the use case and domain with acceptance coverage first; then connect the repository, anti-corruption layer, HTTP and development adapters, and entry.

## Decisions

- Use the `orders` module and `ListCustomerOrdersUseCase.execute(customerId)` returning order props, rather than introducing an inbound web server the request does not require.
- The application sorts by placement instant descending, rather than relying on backend ordering; equal instants have no additional public ordering guarantee.
- Return a complete array without pagination, rather than inventing a paging protocol absent from the service contract.
- Keep placement dates as validated ISO timestamp strings in props and compare their parsed instants, rather than comparing strings or exposing mutable Date objects.
- Map resource records to domain props in the repository; retain snake_case only in the ACL and adapters, rather than letting the service vocabulary enter the use case.
- Use `NODE_ENV=development` for the in-memory backend (empty by default, constructor-seedable); all other environments use HTTP and require `ORDERS_API_URL`, rather than silently falling back to development data.
- Translate invalid records to `ValidationException` and resource/configuration failures to `OrdersUnavailableException` with the original error as cause; reject the query rather than returning partial data or disguising failure as an empty list. No retry policy or public HTTP error status is introduced.
- Use generated acceptance tests with a fake repository in phase 1 and repository integration tests with an ACL-typed in-memory adapter in phase 2, rather than real network calls in local tests.
- The cents architecture decision below is explicitly requested by the user; it is already authorized.

## Architecture decisions

### Decision: money-in-integer-cents · Money amounts use integer cents

@adds @area:product @topic:money @applies:domain,application,infrastructure,adapters @enforced:domain-and-acl-schemas,integration-tests,review

Money amounts SHALL be represented as integers in cents across the product. `OrderProps.totalCents` and service `total_cents` SHALL carry the same cents value without division, rounding or conversion into floating-point major currency units. JavaScript number values SHALL pass safe-integer validation so the representation preserves exact cents.

**Why** The user explicitly requires integer cents; retaining that unit avoids rounding and unit ambiguity at boundaries.

**Alternatives** Decimal major units and floating-point currency values are discarded because they weaken the required representation.

**Consequences** Future money fields must preserve this unit. Values outside the safe-integer range are rejected, not rounded. Currency, sign restrictions and exchange rates are outside this decision.

/**
 * `factory generate [--check]`: the tests come from the specs.
 *
 * Every product spec the configured `productSpecs` glob finds
 * (`openspec/specs/<module>/<use-case>/spec.md` by default), as it will stand once the changes that
 * validation reports ready are archived, is converted to plain Gherkin in memory
 * (opsx-gherkin) and piped into feat2test, which writes
 * `<acceptance>/<module>/<use-case>.feature.test.ts` next to the step adapter the implementer writes
 * (`<use-case>.feature.steps.ts`, scaffolded on the first run and kept afterwards).
 *
 * In the repository that develops the schemas, its own tests are generated the same way: every
 * `openspec/specs/architecture/<layer>/spec.md` whose name is a layer of some workstream becomes
 * `workstreams/<workstream>/<layer>.feature.test.ts`, and any other capability is generated into
 * the folder that holds its adapter, `<capability>.feature.steps.ts` (`review/`, a validator's
 * folder). A capability with neither (`linting`) is verified by running the pipeline, not
 * generated.
 *
 * `--check` only verifies the tests are fresh; `--product-specs <glob>` overrides the configured glob.
 */
export const generate = async (args) => {
    const check = args.includes("--check");
    const flag = args.lastIndexOf("--product-specs");
    const productSpecs = flag >= 0 ? args[flag + 1] : config.productSpecs;
    let failed = false;
    const write = (spec, dir, name) => {
        const gherkin = runTool("opsx-gherkin", [spec], { bin: "opsx-to-feature" });
        if (gherkin.status !== 0) {
            failed = true;
            console.error(`${spec}: ${String(gherkin.stderr).trim()}`);
            return;
        }
        const generated = runTool("feat2test", [
            "generate",
            dir,
            "--stdin",
            "--format",
            "feature",
            "--source",
            `${name}.feature`,
            "--runner",
            "vitest",
            ...(check ? ["--check"] : []),
        ], { input: gherkin.stdout, stdio: ["pipe", "inherit", "inherit"] });
        if (generated.status !== 0)
            failed = true;
    };
    if (DEVELOPING) {
        const adapters = new Map(globSync("**/*.feature.steps.ts", {
            cwd: PACKAGE_ROOT,
            exclude: (f) => ["node_modules", "dist", "workstreams"].includes(f),
        }).map((f) => [basename(f, ".feature.steps.ts"), join(PACKAGE_ROOT, dirname(f))]));
        for (const spec of globSync("openspec/specs/**/spec.md").sort()) {
            const capability = basename(dirname(spec));
            const owner = spec.startsWith(`${ARCHITECTURE_SPECS}/`)
                ? ownerOf(architecture.workstreams, capability)
                : undefined;
            const dir = owner ? join(WORKSTREAMS_DIR, owner.id) : adapters.get(capability);
            if (dir)
                write(spec, dir, capability);
        }
    }
    let merged;
    try {
        merged = await mergedSpecs(PROJECT_ROOT);
    }
    catch (e) {
        console.error(e instanceof Error ? e.message : String(e));
        return 1;
    }
    try {
        const from = merged?.root ?? PROJECT_ROOT;
        for (const spec of globSync(productSpecs, { cwd: from }).sort()) {
            const useCase = basename(dirname(spec));
            const module = basename(dirname(dirname(spec)));
            const dir = `${config.acceptance}/${module}`;
            if (!check)
                mkdirSync(dir, { recursive: true });
            write(join(from, spec), dir, useCase);
        }
    }
    finally {
        merged?.dispose();
    }
    return failed ? 1 : 0;
};

/**
 * The parts of the harness that differ from what was installed or generated, each as a finding that
 * names its part.
 */
export const alteredHarness = (root) => {
    const found = [];
    const fresh = command(root, "generate", "--check");
    if (fresh.status !== 0)
        found.push(`generated tests: they differ from what their specs generate; run \`pnpm exec factory generate\` and leave them as it writes them\n${fresh.output}`);
    const installed = readInstalled(root)?.installed;
    for (const schema of installed?.schemas ?? [])
        if (!schemaLinkHolds(root, schema))
            found.push(`installed schemas: openspec/schemas/${schema} no longer leads to the schema inside the installed command; run \`pnpm exec factory doctor --fix\``);
    const status = spawnSync("git", ["status", "--porcelain", "--", "factory.config.ts"], {
        cwd: root,
        encoding: "utf8",
    });
    if (status.status === 0 && status.stdout.trim())
        found.push("factory configuration: factory.config.ts differs from what is committed; the person edits and commits it, an agent restores it");
    const lock = join(root, "apm.lock.yaml");
    if (existsSync(lock)) {
        const skills = Object.values(PLACES).map((place) => `${place.skills}/`);
        const { dependencies = [] } = (parse(readFileSync(lock, "utf8")) ?? {});
        const altered = dependencies
            .flatMap((d) => Object.entries(d.deployed_file_hashes ?? {}))
            .filter(([path]) => skills.some((folder) => path.startsWith(folder)))
            .filter(([path, hash]) => {
            const file = join(root, path);
            const now = existsSync(file)
                ? `sha256:${createHash("sha256").update(readFileSync(file)).digest("hex")}`
                : "absent";
            return now !== hash;
        })
            .map(([path]) => path);
        if (altered.length)
            found.push(`agent skills: ${altered.slice(0, 5).join(", ")}${altered.length > 5 ? ` and ${altered.length - 5} more` : ""} differ from what was installed; install the package again`);
    }
    if (installed?.guards.length)
        for (const agent of installed.agents) {
            const unwired = unwiredGuards(root, agent);
            if (unwired.length)
                found.push(`agent guards: ${PLACES[agent]?.hooks} no longer calls ${unwired.join(" or ")}; install the package again`);
        }
    return found;
};
/**
 * The checks of the phase a change is building: the rules of the workstreams its tasks name, with
 * those upstream of them, and the product tests those workstreams are proved by.
 */
export const phaseChecks = async (root, change) => {
    const phase = change.plan.phases.find((p) => p.tasks.some((t) => !t.done));
    if (!phase)
        return [];
    const [config, schema] = [
        await projectConfig(root),
        await loadSchema(projectSchemaName(root)),
    ];
    const upstream = (id, seen = new Set()) => {
        for (const d of config.workstreams[id]?.dependsOn ?? [])
            if (!seen.has(d))
                upstream(d, seen.add(d));
        return seen;
    };
    const named = [
        ...new Set(phase.tasks.flatMap((t) => (t.workstream ? [t.workstream] : []))),
    ].filter((id) => id in schema.workstreams);
    const covered = new Set(named.flatMap((id) => [...upstream(id)]));
    const found = [];
    for (const id of named.filter((id) => !covered.has(id))) {
        const r = command(root, "check", "--workstream", id);
        if (r.status !== 0)
            found.push(`the check of ${id} fails:\n${r.output}`);
    }
    const kinds = new Set([...new Set([...named, ...covered])].flatMap((id) => schema.workstreams[id]?.tests ?? []));
    for (const kind of kinds) {
        const r = command(root, "test", kind);
        if (r.status !== 0)
            found.push(`the ${kind} tests fail:\n${r.output}`);
    }
    return found;
};
/**
 * Judges an agent's attempt to finish in the project at `root`. With no change in implementation it
 * holds nobody. Otherwise the harness must be as installed and generated and the checks of the phase
 * must pass; a failure sends the agent back, and the third in a row lets it finish with the change
 * recorded as waiting for the person.
 */
export const gate = async (root, { checks = phaseChecks } = {}) => {
    const building = await changesInImplementation(root);
    if (!building.length)
        return { allowed: true, findings: [] };
    const altered = alteredHarness(root);
    const refused = [];
    const handed = [];
    for (const change of building) {
        const findings = altered.length ? altered : await checks(root, change);
        const path = recordPath(root, change.name);
        if (!findings.length) {
            rmSync(path, { force: true });
            continue;
        }
        const failures = readGate(root, change.name).failures + 1;
        const record = {
            failures,
            waitingFor: failures >= ATTEMPTS ? "the person" : "the agent",
            findings,
        };
        writeFileSync(path, `${JSON.stringify(record, null, 2)}\n`);
        if (failures >= ATTEMPTS)
            handed.push(`${change.name} failed to finish ${failures} times in a row and now waits for the person: ${join(CHANGES, change.name, RECORD)} holds what was found`);
        else
            refused.push(`${change.name} is in implementation and cannot be left like this (attempt ${failures} of ${ATTEMPTS}):`, ...findings);
    }
    return { allowed: refused.length === 0, findings: refused.length ? refused : handed };
};
/**
 * `factory gate [--helper]`: judges an agent's attempt to finish, read from the hook's input. Exit
 * status 2 with the findings on standard error sends the agent back; 0 lets it finish.
 */
export const run = async (_args) => {
    const cwd = hookInput().cwd ?? process.cwd();
    const verdict = await gate(projectOf(process.env.CLAUDE_PROJECT_DIR || cwd));
    for (const finding of verdict.findings)
        console.error(finding);
    return verdict.allowed ? 0 : 2;
};

const isSection = (v) => typeof v === "object" && v !== null && !Array.isArray(v);
const merge = (base, over) => {
    if (over === undefined)
        return base;
    if (!isSection(base) || !isSection(over))
        return over;
    const out = { ...base };
    for (const [k, v] of Object.entries(over))
        out[k] = merge(base[k], v);
    return out;
};

 * The project configuration over the defaults: a value it sets replaces the default (arrays
 * included), a section it sets is merged key by key, and whatever it leaves out keeps its default.
 * Without a project configuration, the defaults as they are.
 */
export const resolveConfig = (defaults, project) => merge(defaults, project);

# OpenSpec and Gherkin compatibility

Preserve the intended behavior while expressing it in the requested format.
Read the [canonical compatibility contract](references/OPENSPEC_MDG_PROFILE.feature.md)
in full before authoring or changing a compatible specification. Its Rules and
Scenarios specify the converter and demonstrate the format. Apply that structure
and its compatibility constraints to the requested domain's behavior. The contract
defines the supported mappings; this entry point explains how to use them.

## Select the representation

| Input | Output | Command |
| --- | --- | --- |
| Markdown with Gherkin | OpenSpec | `opsx-gherkin mdg-to-opsx` |
| OpenSpec | Markdown with Gherkin | `opsx-gherkin opsx-to-mdg` |
| OpenSpec | Plain Gherkin | `opsx-gherkin opsx-to-feature` |

These are the supported conversion directions. Plain `.feature` is an output
and a directly validatable format; it is not a converter input.

After reading the contract, choose a complete example for the constructs you need:

- Basic main spec: [minimal.feature.md](references/examples/minimal.feature.md),
  with a Feature description, a software target, one normative Rule, and a single-row Outline;
  equivalent [OpenSpec](references/examples/minimal.openspec.md) and
  [plain Gherkin](references/examples/minimal.feature).
- Shared setup, outlines, multiple Examples groups, Data Tables, and Doc Strings:
  [account.feature.md](references/examples/account.feature.md), with
  [OpenSpec](references/examples/account.openspec.md) and
  [plain Gherkin](references/examples/account.feature) counterparts.
- Delta operations: [authentication-delta.feature.md](references/examples/authentication-delta.feature.md)
  with [OpenSpec](references/examples/authentication-delta.openspec.md) and
  [plain Gherkin](references/examples/authentication-delta.feature) counterparts.
  This is a structural change document; each added/modified behavior still needs
  a complete example, while removal/rename entries retain their restricted shape.
- Finding and retrieving the contract: [profile-access.feature.md](references/profile-access.feature.md).

These examples apply the canonical contract to their own domains.

## Author within the contract

- Model each completed Feature as one whole public use case. Give each scenario
  its own necessary prior facts, one action or query, and observable consequences.
  Keep acceptance and rejection in separate scenarios of the same use case.
- Expose meaningful example values as named Outline arguments, even for one row.
  Keep independent roles distinct, such as stored/submitted credentials and
  requested/resulting quantities. Keep fixed criteria in Rules, cohesive records
  in Data Tables, and literal source text intact when the use case examines it.
- Match the requested representation: Gherkin headings and bullet steps in MDG,
  OpenSpec requirement headings and bold step keywords in OpenSpec, native
  keyword lines in `.feature`. A fenced native document is not MDG structure.
- Use the contract's Feature/Purpose, Rule/Requirement, Background, and
  Scenario mappings. Supply a meaningful main-spec Purpose and the required
  `SHALL` or `MUST` wording for ordinary Rules and ADDED/MODIFIED requirements.
- Place descriptions before their child structures. Keep each Background in
  its intended scope; preserve the original step roles and all example values.
- Use English structural keywords supported by this profile. Do not translate
  keywords or rewrite domain content merely to make conversion succeed.
- Bind outline placeholders with concrete Examples rows. Keep Examples groups,
  their tags, and step Data Tables distinct. Follow the contract's indented
  Markdown table syntax and escaping. Check parsed row counts and literal
  values, especially pipes, backslashes, newlines, and Doc String contents.
- Identify a completed Feature's verification boundary: `@code` for software,
  `@skill` for an agent applying guidance, `@prompt` for a model executing a prompt,
  or `@plugin` for its host integration. The software teaching examples use `@code`.
  These tags identify the exercised boundary, not its internal dependencies.
  Descriptive topic tags are optional and need not be copied from the contract.
- Conversion accepts compatible untagged documents and plain Scenarios too.
  Preserve their existing model; do not insert targets or invent parameters
  while converting. Authoring conventions do not narrow syntax acceptance.
- In MDG, put each tag in its own backtick span immediately above the tagged
  heading. In native Gherkin, use bare tags. Reserve `@openspec-*` and `@mdg-*`
  names for the structural roles defined by the contract.
- For deltas, mark the Feature and each operation as the contract specifies.
  REMOVED supports the requirement name only. RENAMED supports its canonical
  FROM and TO names only. Additional removal/rename content has no mapping;
  report that boundary instead of silently deleting information.

### Keep table and argument values intact

Indent Markdown table rows by two spaces. In MDG, put data rows directly after
the header, without a separator row; the converter emits this canonical form.
OpenSpec tables retain their Markdown separator row. The pinned MDG parser
accepts either input form and preserves the interpreted rows; table formatting
must not change Examples cases or Data Table values. Plain Gherkin also omits
separators. Use `\|` for a literal pipe, `\\` for a literal backslash,
and `\n` for a newline inside a cell. Do not apply cell escaping to Doc Strings.

Keep a Markdown Doc String in a triple-backtick block indented by two spaces
under its step; put its optional media type immediately after the opening fence.
Preserve the content's indentation relative to the fence. In an outline, each
`<placeholder>` names an Examples column; retain every intended data row and
verify the expanded cases. The account example demonstrates two separate
Examples groups and a JSON Doc String containing a placeholder.

## Convert and verify

Each converter accepts one path, `--text`, or stdin. Use stdout to inspect a
result; use `-o <destination>` for an explicit output file. Existing outputs
require `--force`. Respect the user's destination and overwrite intent.

```sh
opsx-gherkin mdg-to-opsx input.feature.md -o spec.md
opsx-gherkin opsx-to-mdg spec.md -o output.feature.md
opsx-gherkin opsx-to-feature spec.md -o output.feature
```

Use `--name` when OpenSpec text has no title or usable source-path context.
`--project-root` supplies existing main-spec context for delta validation when
needed. Consult a converter's `--help` for its exact options.

The converters validate both endpoints and reject changes to the normalized
model before emitting output. Formatting may become canonical; names, values,
structure, and supported metadata must retain their meaning.

Direct endpoint validation checks syntax rather than conversion eligibility.
The standalone OpenSpec validator below accepts main specifications. For deltas,
use a supported conversion: it invokes the official strict delta validator and
checks model preservation.

```sh
validate-spec --format openspec spec.md
validate-spec --format mdg input.feature.md
validate-spec --format feature output.feature
```

Passing these checks establishes example syntax and conversion preservation.
Review the authored scenarios against the requested domain behavior as well;
validator success alone does not establish reliable agent authoring.

With npm/npx, use `npx opsx-gherkin <command>` for the main CLI and
`npx --package opsx-gherkin validate-spec ...` for the standalone validator.
`opsx-gherkin profile` prints the same contract linked above.

Exit status `1` means invalid input, unsupported profile content, or failed
conversion validation; `2` means usage or I/O failure. Read stderr and correct
the indicated issue without inventing a mapping or changing the intended
behavior. If the CLI is unavailable, explain the syntax from the contract and
state that execution has not been verified.

# Gherkin Craft

Input: requirements for programmed software. Output: Gherkin whose named steps
map to Step Adapter methods and whose examples drive the tests feat2test
generates. Read [the generator contract](references/generator-contract.md) and
[format and language](references/gherkin-format.md) before writing or
reviewing. Use [the authoring guide](references/authoring-guide.md) for worked
examples when choosing a formulation.

## Every step is named

End every step with one HTML comment naming its Step Adapter method:
`When <quantity> units are added <!-- addUnits -->`. The name is the step's
identity and the words are documentation; feat2test rejects a step without one
(`MISSING_STEP_NAME`) or with a malformed one (`INVALID_STEP_NAME`). Names are
camelCase, English by default, representative and semantically loaded: they
state the action or fact (`<!-- confirmOrder -->`), never a position or filler
(`<!-- step1 -->`, `<!-- doIt -->`). Give one fact one name across the Feature,
even where its wording differs, and keep each name to one keyword role and one
input shape. Markdown preview hides the names; they stay visible in the source
and in `.feature` files, and no other marker syntax replaces them.

Put every value that varies between examples in a placeholder, never in the
words. Bind every placeholder in every row, including those in titles and
DataTables, which the generator does not catch. The generated test only calls
steps, so each Then step carries the value it checks
(`the order total is <total> <!-- orderTotal -->`), not a verdict
(`the total is correct <!-- totalIsCorrect -->`).

## One Feature per use case

Each Feature is one complete use case at the software's boundary: relevant prior
facts, one whole action or query, and the observable answer or changed or
preserved state. Rules and outcome variants of that use case, acceptance and
rejection included, stay together in distinct scenarios. Distinct purposes get
separate Features even when they share data; shared quantities keep one meaning.
No human actor is required when the domain has none.

Specify what the software answers, changes or preserves, not how. Replace a step
that describes implementation
(`the repository save method is called <!-- repositorySaveCalled -->`) with its
observable result. Internal call order, algorithms, runners, languages and
output layout are not acceptance criteria and never become steps or Examples
columns.

## Meaningful arguments

- Expose identities, quantities, units, categories, relative positions,
  negative facts and expected results as named arguments in a
  `Scenario Outline`, even with one justified row.
- Keep independently variable roles apart even when their values coincide: a
  horizon, a reporting interval and a recurrence interval of seven days are
  three arguments with explicit units, not one `days`.
- Keep a cohesive record or collection as one DataTable, not many scalar
  columns. To vary whole records, give each an identity in the table and select
  it from Examples.
- Keep fixed rule criteria fixed. A diagnostic may bind the fixed value without
  making the criterion configurable. Never replace actions, conditions or
  diagnostics with prose-valued arguments such as `<reason>`.
- Preserve subjects, negation, quantifiers, units, timing, relative selectors
  and causes. Use explicit absence, not blank cells or `null`. Supply raw input
  when its derivation is what the use case examines.

## Discriminating examples

Ask whether each example would still pass if a factor or rule were ignored; a
factor of one hides a missing multiplication. Cover meaningful partitions,
boundaries and failures, and keep unknown, absent, zero and invalid distinct.
Recognize coverage already present and keep it on revision.

A boundary belongs here when the domain expert would recognize it as their rule:
a zero price, a repeated item, an amount shown with two decimals. A value that
matters only because of machine representation (binary floating point, time
zones, text normalization, overflow) is left out and named as a candidate for
downstream programmatic tests, which are not written in Gherkin.

Inspect relevant state/event pairs, repeated requests, missing information and
mixed independent dimensions. A rejection states what was preserved; a query
checks its answer without inventing a mutation. Each scenario supplies its own
context and never depends on another having run. Parsing or a small
cross-product does not prove exhaustive coverage.

## Unresolved rules stay out of tables

Separate what the requirements assert, what is justifiably inferred and what is
undecided. When a row's expected outcome depends on an undecided rule, such as a
rounding or validity policy, omit that row, state the open decision and deliver
the supported rows. One supplied instance exposes a relationship's arguments; it
does not establish behavior for members the source does not support.

## Tags

Tags are metadata the generator does not interpret. None is required, including
`@code`; they only serve the project's own runner filters or conventions.
Preserve tags already present when revising.

## Validate with the generator

When feat2test is installed, run `feat2test validate` on the delivered Feature
through its file, `--text` or `--stdin`, with the project's runner and `--json`.
Report the example count and diagnostics; it writes nothing. When it is not
installed, check the format reference and say generator validation was not run.
Validation proves generability, not semantic review.

Write specifications in English unless the user or the project's `CLAUDE.md` or
`AGENTS.md` explicitly asks for another language for them. Method names stay
English unless the user explicitly asks for another language for the methods
too; see [format and language](references/gherkin-format.md).

## Review checklist

Apply to the complete specification against the requirements and the user's
constraints, whether or not another agent is available. Cite the scenario and
evidence for each finding, and separate wording defects from undecided domain
rules.

- [ ] Each Feature is one use case; distinct purposes are separate Features.
- [ ] Every step ends with a representative `<!-- name -->`, English unless chosen otherwise.
- [ ] Each fact has one name; each name has one role and one input shape.
- [ ] Every placeholder is bound in every row, including titles and DataTables.
- [ ] Every Then step carries the expected value it checks.
- [ ] No prose-valued arguments; roles, units and fixed criteria are explicit.
- [ ] Examples discriminate factors, boundaries and failures; prior coverage kept.
- [ ] No invented rules; open decisions are stated, not tabled.
- [ ] Steps describe observable behavior, not implementation or tooling.
- [ ] Syntax matches the format reference; `feat2test validate` passes when available.

A review-only request returns findings and edits nothing. A revision fixes every
affected occurrence of a shared step or argument and keeps justified behavior.

/** The active changes that validation reports ready and that hold delta specs, oldest first. */
const readyWithDeltas = async (root) => {
    const found = [];
    for (const name of activeChanges(root)) {
        const change = readChange(root, name);
        if (!change?.deltaSpecs.length)
            continue;
        try {
            if ((await validateChange(root, name)).ready)
                found.push({ name, created: change.created ?? "" });
        }
        catch (e) {
            if (!(e instanceof NotValidatable))
                throw e;
        }
    }
    return found
        .sort((a, b) => a.created.localeCompare(b.created) || a.name.localeCompare(b.name))
        .map((c) => c.name);
};
