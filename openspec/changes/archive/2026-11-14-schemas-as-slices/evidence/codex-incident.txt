# plan

The artifacts are the handoff: everything decided ends up in the plan or in a delta spec.

1. `pnpm exec factory doctor`. When it prints anything as `missing` or `drift`, follow the `setup` skill first. A `note` is for the person: relay it once and go on.
2. Decide whether the intention changes anything: behaviour, code, a standing decision or a procedure. A question about the system changes nothing: answer it and stop here. An intention about a change that is already open belongs to the `feedback` skill.
3. Choose the schema. `pnpm exec factory schemas` lists the schemas this project has, when each one is used and the workstreams it builds through. Pick the one whose use covers the intention. When the intention needs two of them, open one change per schema, and write under Decisions of each plan the name of the other change and what it leaves to it. When no schema covers the intention, open no change: tell the person which schemas the project has and stop.
4. Open the change: `pnpm exec factory openspec new change <name> --schema <schema>`, the name a short kebab-case phrase of what changes.
5. Read what stands: the specs under `openspec/specs` the intention touches, and everything under `openspec/adr` and `openspec/runbooks`.
6. When the schema has workstreams, read the skill of each one the change will touch, under the `implement` skill's `references/workstreams/<workstream>/SKILL.md`. Its Owns line says where that workstream's files live and how they are named: a seam is signed in those folders and with those names.
7. `pnpm exec factory openspec status --change <name> --json` lists the artifacts of the change's schema. For each one, `pnpm exec factory openspec instructions <artifact> --change <name> --json` gives its instruction and its template: write the artifact as that instruction says. Write the whole first proposal from your own decisions before asking the person anything. The plan's instruction says which decisions are the person's; those go under Open questions, each with the option you picked.
8. `pnpm exec factory validate <name>` and fix every finding that is yours to fix.
9. Show the person the open questions. When they answer, record each answered decision in its artifact and remove its question in that same update, then validate again.

The plan is done when `pnpm exec factory validate <name>` prints `ready`. Tell the person and stop: building it is the `implement` skill, in a run the person starts.

+## Procedures
+
+### Procedure: orders-production-outage · Diagnose orders service 503s in production
+
+@adds @purpose:diagnose @topic:orders-outage @env:production
+
+**When** Orders returns 503s, its error rate rises, or a responder investigates a past outage. A reported ten-minute 503 incident prompted this procedure; its exact timestamps and cause are not established here.
+
+**Requires** Access to the cloud console with the on-call role, production orders request/error telemetry, and connection telemetry for the database used by orders. Use an existing authenticated console session and select the on-call role. No additional secret is required by this procedure; temporary session credentials remain in the authenticated console session and must not be copied into this document or incident notes. If the session is unavailable, use the organization's existing console sign-in process. Missing access or telemetry follows step 6; do not guess an account, region, database, credential store, or dashboard URL.
+
+**Steps**
+
+1. Establish the UTC incident start and end from the report or alert. For an ongoing incident use the current time as the provisional end. Record the source and uncertainty. Inspect the incident interval plus ten minutes on each side, and use the preceding thirty minutes as a baseline. Confirm the production account/environment and orders service using console resource context before interpreting any telemetry.
+2. Check **error rate first**. In the available production orders request telemetry, compare failed requests divided by total requests with the baseline over matching one-minute intervals. Record total request count, failure count/rate, 503 count, onset, peak and latest interval. Use an existing documented error definition if present; otherwise use HTTP 5xx and label that choice in the incident notes. If only logs are available, calculate a rate only when they contain all requests with known coverage; otherwise record observed errors and mark the rate unavailable. Zero requests gives an undefined rate, not evidence of health. Missing telemetry does not prevent the next check, but must be recorded.
+3. Check **database connections second**, using the same incident and baseline windows. Identify the database from the orders resource configuration or dependency view. Inspect active/open connections relative to its configured maximum and, where exposed, orders pool usage, waiting requests, connection timeouts and refused connections. Record timestamps and available counts/limits. A rise in errors alongside connections near their limit, waiters or connection failures suggests connection pressure; correlation alone does not establish the cause. Normal connection counts leave other causes open; unavailable limits or metrics remain explicitly unverified.
+4. In the cloud console, with the **on-call role**, open log group **`/prod/orders`** in the confirmed production resource context. Select the same UTC window. Inspect 503 and error entries first, then surrounding entries across relevant log streams. Look for database connection, pool, timeout or refusal messages and compare their timing with steps 2 and 3. Capture timestamps, log links, error signatures and request/correlation IDs where present, redacting credentials and customer data. If the group is absent or empty, confirm resource context, time range and filters once, then record the gap and follow step 6.
+5. Write a diagnostic handoff: service/environment, UTC window, customer impact known so far, error-rate findings, database-connection findings, log evidence, a working hypothesis, competing explanations and missing evidence. Label facts separately from hypotheses. For an ongoing incident, refresh the latest error and connection observations every five minutes. This procedure authorizes observation only; remediation follows the incident owner's existing process.
+6. If access is denied, telemetry is missing, or the cause remains unclear after these checks, hand the evidence and exact blocker to the existing production incident owner through the established incident process. Include the failed console action and resource context for access gaps, without credentials. Request the database responder through that process when connection pressure is suspected. If no owner can be identified, use the organization's existing on-call escalation route; do not invent a contact or delay handoff while searching for a root cause.
+
+**Verification** The handoff contains the selected resource context and UTC window, an error-rate result or explicit evidence gap recorded before a database-connection result or gap, and evidence from `/prod/orders` or the precise access/data blocker. Diagnosis is complete when the findings and unresolved evidence have a named incident owner; an unknown root cause is explicitly recorded. Mark observed service recovery only when request traffic is present and the error rate has returned to the pre-incident baseline for ten consecutive one-minute intervals. Record database-connection status separately; recovered traffic does not prove the cause or close the incident. If these observations are unavailable, leave recovery unverified and hand off.
