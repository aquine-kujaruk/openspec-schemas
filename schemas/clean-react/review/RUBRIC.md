# React architecture review

What no linter can decide about the React framework layer of `clean-react`: the judgement rules `factory review` asks after the rows of the clean core.

### Reviewer rubric (not lintable; judged by `factory review`)

Each row carries the yes/no question `factory review` asks the decision model and the layers (a folder or subfolder, `framework/stores`) it is asked over. A question is generic: it names no package of the project's `package.json` and no word of the product vocabulary. A row id belongs to one rubric: these rows never repeat an id of the core's.

Product vocabulary (each word is matched at the start of a word; a question that names one is rejected): `payment`, `cart`, `order`, `invoice`, `coupon`, `refund`, `report`, `notification`, `profile`, `auth`, `session`.

| ID  | Rule | Question (yes/no; the model reads it) | Layers |
| --- | ---- | ------------------------------------- | ------ |
| S01 | The hook decides _when_ and _what_ to show; the use case decides _what happens_. A business condition in a controller is misplaced. Business exceptions are thrown by the use case or the domain, never by the repository. Validating twice (controller and use case) is a smell | Does this file place a business decision where it does not belong: a business condition inside a controller or hook, a business exception thrown from a repository, or a validation repeated in both a controller and a use case? | framework, infrastructure |
| S02 | One store per URL page, named after it, keeps every state that changes on that page (step, form draft, selection, filter, messages, the chosen basket). What comes from a fetch or a mutation lives in the query cache (key, stale time, data set by hand, initial data from the list's cache), never duplicated in the store; what the query layer already exposes (pending, variables, error) is not copied to the store | Does this store keep data that came from a fetch or a mutation, or copy a flag the query layer already exposes, instead of holding only the flow in progress (step, draft, selection, messages)? | framework/stores |
| S03 | The controller returns only what the markup paints; minimal props (a `Pick<>` of the controller when a component uses part of it); declarative names (`isSelected`, `isEmpty`, never `a === b` or `.length` in the markup: `jsx-neither-compares-nor-counts`). Error texts and limits come from the controller, the view model or the domain, never written in the markup | Does the controller expose a property that its rendering view never reads, or does the view compare values, count a collection, or supply a literal error message or limit in its markup? Compare each exposed property with its use in the supplied view. | framework |
| S04 | A view model exists only when the view does not read the same as the domain or is interactive (a form). A form view model (`{ value, error }` per field) bridges the domain validation: it calls the aggregate or the schema and spreads the errors per field; it does not reimplement rules or ranges. Validation is decided once (in the domain) and translated to the view once (in the view model) | Does this view model reimplement a domain rule or range instead of calling the domain validation and distributing its errors per field, or exist where the view reads the same as the domain? | framework |
| S21 | When no use case stands between the query and the repository, the query hydrates what it reads into domain objects with its select step; raw props never reach the view | Does this query hand raw records or schema props to the view, instead of domain objects hydrated by a use case or by the query's select step? | framework/queries |
| S22 | A view model is not a DTO: it keeps its rules and only decides variations of the canonical format (abbreviate, hide cents, the screen's locale); the canonical representation of a value object belongs to the domain | Does this view model rebuild the canonical representation of a value object, or merely copy fields into a transport shape, instead of deciding only how the view varies that representation? | framework/view-models |
| S23 | Once implemented, a page, a component or a controller keeps no changing state in `useState` or `useReducer` where its page's store can hold it; a justified exception is the reviewer's call. A stub controller `react-ui` writes is exempt: it keeps its literal data in local state, and `react-hooks` replaces it | Does this page, component or controller keep a changing state in local component state (useState, useReducer) that the store of its page could hold instead? | framework/ui, framework/controllers |
